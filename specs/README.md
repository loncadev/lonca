# OpenAPI spec collection

Curated, per-service OpenAPI documents for the Turkish marketplaces that Lonca integrates with.
The collection exists so that:

- developers can read (or generate clients from) a machine-readable definition instead of scraping
  a developer portal;
- the SDKs in [`sdks/`](../sdks/) can be checked against the published contract;
- the planned drift-detection job ([Vision](../README.md#vision), stage 2) has a tracked baseline
  to diff a fresh capture against.

## Layout

```
specs/
  README.md                       ← this file
  <marketplace>/
    README.md                     ← provenance, licence, SDK coverage, known gaps
    manifest.json                 ← index of the files below (generated)
    <service>.json                ← one standalone OpenAPI 3.x document per upstream service
```

- One file per **upstream service** (host or host + base path), named after that service as
  the marketplace itself names it (`oms-external`, `mpop-catalog`, ...), not after the SDK
  resource that consumes it.
- Every file is a self-contained document: `openapi`, `info`, `servers`, `paths` and only the
  `components` its own operations reference. No `$ref` points outside the file.
- Files are generated by a script under [`scripts/specs/`](../scripts/specs/) from a source
  that is **not** tracked in git (raw portal dumps are large and unreviewed). The script is
  deterministic: paths are sorted, HTTP methods are in canonical order, schema names are sorted,
  and output is 2-space `JSON.stringify` so diffs are reviewable. `specs/**/*.json` is excluded
  from prettier for that reason.
- `x-lonca-*` extension keys carry provenance (`info.x-lonca-source`) and per-operation portal
  timestamps (`x-lonca-portal-updated-at`); everything else is the upstream definition as
  captured.
